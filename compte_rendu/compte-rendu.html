CoreDNS assure la résolution DNS interne pour les conteneurs. Il résout les noms *.tpiam.internal et relaie les autres requêtes vers DNS4EU. 

docker compose -f compose\dns\compose.yml up -d

Test de résolution :

nslookup portail.tpiam.internal 127.0.0.1
nslookup google.com 127.0.0.1
📸Capture : nslookup résolvant portail.tpiam.internal → 127.0.0.1
Si le port 53 est déjà occupé par le service "Client DNS" de Windows, le désactiver :
Stop-Service -Name "Dnscache" puis Set-Service -Name "Dnscache" -StartupType Disabled

Étape 9 PKI — Lancement de StepCA

StepCA (Smallstep) est notre Autorité de Certification privée. Elle joue le rôle de Let's Encrypt mais pour notre infrastructure interne. Elle émet les certificats TLS de tous les services via le protocole ACME.

Premier lancement en mode attaché pour récupérer le mot de passe JWK :

docker compose -f compose\stepca\compose.yml up
Le mot de passe du provisioner JWK s'affiche dans les logs au premier démarrage. Le noter immédiatement.
📸Capture : logs StepCA avec le mot de passe JWK visible

Relancement en mode détaché :

docker compose -f compose\stepca\compose.yml up -d

Inspection des certificats

Depuis la console du container step-ca (via Dockhand) :

step certificate inspect $(step path)/certs/root_ca.crt
step certificate inspect $(step path)/certs/intermediate_ca.crt
📸Capture : inspection du certificat root CA (Subject, Validity, Key Usage)

Changement du mot de passe de la clé intermédiaire

step crypto change-pass $(step path)/secrets/intermediate_ca_key

Saisir l'ancien mot de passe (JWK), puis définir le nouveau. Mettre à jour le fichier secrets/password.

Création d'un certificat de test

step certificate create test.subject test.csr test.key --csr
step certificate inspect test.csr
📸Capture : CSR généré et inspecté avec succès
Étape 10 PKI — Configuration ACME avec Caddy

On configure Caddy pour obtenir ses certificats TLS auprès de StepCA via ACME, exactement comme Let's Encrypt mais avec notre CA privée.

Récupération du certificat root

Depuis la console du container step-ca :

cat $(step path)/certs/root_ca.crt

Copier le contenu PEM dans compose/caddy/root-ca.pem.

Mise à jour du Caddyfile

Ajout du bloc TLS ACME pour chaque virtual host, pointant vers StepCA :

tls {
  ca https://step-ca:9443/acme/acme/directory
  ca_root /etc/caddy/trusted-roots/root-ca.pem
}

Relancement de Caddy

docker compose -f compose\caddy\compose.yml down
docker compose -f compose\caddy\compose.yml up -d

Vérification dans le navigateur : le certificat de https://portail.tpiam.internal doit être émis par TPiam PKI.

📸Capture : cadenas HTTPS → certificat émis par "TPiam PKI" (et non auto-signé)

Étape 12 SAML — Intégration SimpleSAML / Keycloak

On configure SimpleSAMLphp comme Service Provider (SP) et Keycloak comme Identity Provider (IdP). Le SP délègue l'authentification à Keycloak via le protocole SAML 2.0. Les AuthnRequests sont signées avec un certificat X.509 pour garantir leur intégrité.

12.1 — Configuration du SP (authsources.php)

Ce fichier définit l'identité du SP (entityID), l'IdP cible et les fichiers de certificats pour la signature : 

<?php
$config = [
    'admin' => ['core:AdminPassword'],
    'default-sp' => [
        'saml:SP',
        'entityID'    => 'https://simplesaml.tpiam.internal',
        'idp'         => 'https://idp.tpiam.internal/realms/tpiam',
        'privatekey'  => 'saml.pem',
        'certificate' => 'saml.crt',
    ],
];

12.2 — Métadonnées de l'IdP (saml20-idp-remote.php)

Ce fichier décrit Keycloak côté SP : ses endpoints SSO/SLO, le binding utilisé (HTTP-Redirect) et son certificat de signature (extrait depuis https://idp.tpiam.internal/realms/tpiam/protocol/saml/descriptor). 

<?php
$metadata['https://idp.tpiam.internal/realms/tpiam'] = [
    'entityid'          => 'https://idp.tpiam.internal/realms/tpiam',
    'sign.authnrequest' => true,
    'SingleSignOnService'         => 'https://idp.tpiam.internal/realms/tpiam/protocol/saml',
    'SingleSignOnService.binding' => 'urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect',
    'SingleLogoutService'         => 'https://idp.tpiam.internal/realms/tpiam/protocol/saml',
    'SingleLogoutService.binding' => 'urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect',
    'certData' => '/* certificat X.509 Keycloak */',
];
📸Capture : fichier saml20-idp-remote.php dans l'éditeur

12.3 — Génération du certificat SP (via Keycloak)

Keycloak génère la paire de clés RSA pour le client SP (onglet Keys → Generate new keys). Il conserve la clé publique et exporte un fichier keystore.jks contenant la clé privée.

📸Capture : génération des clés dans Keycloak (onglet Keys du client SAML)

Conversion JKS → PKCS12 via Docker (pas de Java installé sur le host) :

docker run --rm -v "c:\...\TP_PublicKeyInterface-PKI-:/work" eclipse-temurin:21-jre-alpine \
  sh -c "keytool -importkeystore -srckeystore /work/keystore.jks \
         -destkeystore /work/keystore.p12 -deststoretype PKCS12 \
         -srcstorepass password -deststorepass password -noprompt"

Extraction en PEM avec OpenSSL :

# Clé privée
openssl pkcs12 -in keystore.p12 -passin pass:password -nocerts -nodes \
        -out compose/simplesaml/certs/saml.pem

# Certificat public
openssl pkcs12 -in keystore.p12 -passin pass:password -clcerts -nokeys \
        -out compose/simplesaml/certs/saml.crt

12.4 — Import des métadonnées SP dans Keycloak

Pour éviter toute erreur de saisie, on importe les métadonnées XML générées automatiquement par SimpleSAML dans Keycloak. Cela configure automatiquement le bon Client ID, l'ACS URL et le certificat de signature du SP. 

curl -sk https://simplesaml.tpiam.internal/simplesaml/module.php/saml/sp/metadata.php/default-sp \
     -o sp-metadata.xml

Dans Keycloak : Clients → Import client → sp-metadata.xml

📸Capture : client "https://simplesaml.tpiam.internal" importé dans Keycloak
L'ACS URL configurée dans Keycloak doit être exactement :
https://simplesaml.tpiam.internal/simplesaml/module.php/saml/sp/saml2-acs.php/default-sp

12.5 — Configuration du compose SimpleSAML

Deux points critiques dans le compose.yml de SimpleSAML :

  • CONFIG_BASEURLPATH doit être l'URL https complète — sans cela, SimpleSAML génère les callbacks en http:// et Keycloak renvoie une erreur 400 (mismatch ACS URL).
  • Le dossier certs/ est monté dans /var/simplesamlphp/cert/.
environment:
  - CONFIG_BASEURLPATH=https://simplesaml.tpiam.internal/simplesaml/
volumes:
  - ./authsources.php:/var/simplesamlphp/config/authsources.php:ro
  - ./saml20-idp-remote.php:/var/simplesamlphp/metadata/saml20-idp-remote.php:ro
  - ./certs:/var/simplesamlphp/cert:ro
docker compose -f compose\simplesaml\compose.yml up -d --force-recreate

Étape 13 OIDC — Intégration Dockhand / Keycloak

On configure Dockhand pour authentifier ses utilisateurs via OpenID Connect (OIDC). Keycloak joue le rôle d'Authorization Server, Dockhand est le Relying Party. Le flux utilisé est le Authorization Code Flow.

13.1 — Création du client OIDC dans Keycloak

Clients → Create client :

  • Client type : OpenID Connect
  • Client ID : dockhand
  • Client authentication : ON (mode confidential)
  • Standard flow : activé
  • Valid redirect URI : https://dockhand.tpiam.internal/api/auth/oidc/callback
📸Capture : client "dockhand" créé dans Keycloak (onglet Settings)

13.2 — Récupération du Client Secret

Onglet Credentials du client dockhand → copier le Client secret.

📸Capture : onglet Credentials avec le Client Secret

13.3 — Configuration OIDC dans Dockhand

Dans l'interface Dockhand, Settings → Authentication / OIDC :

  • Issuer URL : https://idp.tpiam.internal/realms/tpiam
  • Client ID : dockhand
  • Client Secret : (valeur copiée)

On active l'authentification multi-facteurs (MFA) en rendant l'OTP (One-Time Password) obligatoire pour tous les utilisateurs du realm tpiam.

16.1 — Activation de l'OTP obligatoire

Keycloak → Authentication → Flows → browser :

Changer Browser - Conditional OTP de Conditional à Required.

📸Capture : flux "browser" avec OTP en mode "Required"

16.2 — Première connexion avec OTP

En navigation privée, se connecter avec bob / Bob12345! :

  1. Keycloak affiche la page Configure OTP avec un QR code
  2. Scanner le QR code avec Google Authenticator / Authy / FreeOTP
  3. Saisir le code à 6 chiffres généré → connexion réussie
📸Capture : page Keycloak "Configure OTP" avec QR code
📸Capture : saisie du code OTP et connexion réussie dans Dockhand

16.3 — Vérification aux connexions suivantes

Se déconnecter puis se reconnecter → Keycloak demande directement le code OTP (2ème facteur) sans afficher à nouveau le QR code.

Points clés appris

  • PKI : création d'une CA privée avec StepCA, émission de certificats via ACME
  • SAML 2.0 : configuration SP/IdP, signing des AuthnRequests, gestion des bindings (HTTP-Redirect vs HTTP-POST), extraction de clés depuis un keystore JKS
  • OIDC : Authorization Code Flow, client confidential, callback URI
  • Sécurité : MFA/TOTP obligatoire, politique de complexité des mots de passe
  • Infrastructure : segmentation réseau Docker, reverse proxy HTTPS, résolution DNS interne
